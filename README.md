## Overview

This repository contains representative excerpts from a 9-year documentation archive spanning 900+ user manuals across hardware product lines. ## Background

Producing 900+ user manuals over nine years generated a substantial archive of documentation. This repository curates the most representative samples to answer three questions in 5 minutes:

1. **Can this person write clearly?** (Troubleshooting tables, procedure steps)
2. **Can they design for usability?** (Diagram conventions, information hierarchy)
3. **Can they handle complexity?** (Spec tables, regulatory compliance sections)

The constraint shaping the solution was straightforward: **demonstrate craft without violating copyright.** Every sample has been stripped of brand identifiers, model numbers, and proprietary specifications while preserving the structural decisions that reflect writing skill.

## Sample Rationale

### Monitor Series — Quick Start Sample (Pages 1-4)

**What it shows:** Safety warnings, package contents, product overview diagrams.

**Skills demonstrated:**
- Hierarchy of information (critical safety before setup).
- Diagram labeling conventions (callout numbers, clean line weight).
- Concise introductory copy (under 100 words per section).
- Consistent terminology across sections.

**Why this sample:** Quick starts are the most frequently accessed documentation. If you can't make this clear, nothing else matters.

### Monitor Series — Troubleshooting Sample (Pages 61-63)

**What it shows:** Decision-tree troubleshooting tables with Yes/No branching logic.

**Skills demonstrated:**
- Logical flow design (if/then decision trees).
- Scannable table formatting (clear headers, minimal text).
- Problem-solution pairing (one-to-one mapping).
- Edge case handling ("If problem persists, contact support").

**Why this sample:** Troubleshooting sections require the clearest thinking. Poorly written troubleshooting drives support tickets.

### Monitor Series — Specifications Sample (Appendix)

**What it shows:** Dense technical data organized into categorized tables.

**Skills demonstrated:**
- Information architecture (grouping related specs).
- Unit consistency (metric/imperial dual notation).
- Footnote usage for exceptions and caveats.
- Readability at small font sizes (8pt+).

**Why this sample:** Spec tables are where writers fail most often — cramming too much into unstructured lists. This shows disciplined organization.

### Projector Series — Lamp Replacement Sample

**What it shows:** Step-by-step procedure with exploded-view diagrams and warning callouts.

**Skills demonstrated:**
- Procedural sequencing (logical step order).
- Warning placement (before dangerous action, not after).
- Diagram-to-text alignment (referencing same components).
- Cautionary language precision ("Do not touch" vs. "Avoid touching").

**Why this sample:** Assembly/disassembly procedures are high-risk documentation. Errors cause physical damage or injury.

### Large-Format Display — Installation Guide Sample

**What it shows:** Wall-mounting procedure with VESA specifications and safety warnings.

**Skills demonstrated:**
- Multi-step procedure formatting (numbered lists with sub-steps).
- Specification integration (hole patterns, screw sizes, torque values).
- Risk mitigation language (warnings for fall hazards).
- Cross-referencing ("See VESA mounting standards").

**Why this sample:** Installation documentation has legal liability implications. Precision matters more than brevity.

### Illustration Examples — Port Diagram

**What it shows:** Clean line drawing of rear I/O panel with numbered callouts.

**Skills demonstrated:**
- Vector illustration technique (scalable line weights).
- Label placement (adjacent to callouts, no overlap).
- Visual hierarchy (important ports highlighted).
- Grayscale-first design (accent colors only for emphasis).

**Why this sample:** Technical illustration is a distinct skill from writing. This proves both capabilities.

## Redaction Methodology

All samples underwent this sanitization process:

1. **Brand removal:** Replaced or removed entirely.
2. **Model number scrubbing:** Changed to generic descriptor.
3. **Specification generalization:** Kept spec categories but anonymized exact values.
4. **Contact info deletion:** Removed real addresses, phone numbers, email endpoints.
5. **Trademark check:** Verified no protected feature names remain.

**What was preserved:**
- Document structure and hierarchy
- Writing style and tone
- Diagram conventions and illustration style
- Table formatting and footnote usage
- Warning/caution note structures

See `redaction-notes/sanitization-methodology.md` for the full checklist used during preparation.

## Limitations & Notes

**Sanitized excerpts only.** These are not complete documents. Each sample represents 2-4 pages from a larger manual, selected to demonstrate specific skills. Full context is intentionally omitted to protect proprietary information.

**Static collection.** Unlike the live wiki project or active template repositories, this is a snapshot of work as of 2026. No new samples will be added unless additional products warrant inclusion.

**No interactive elements.** PDFs are flat documents; there's no embedded search, hyperlinks, or multimedia. This reflects the production format at the time, not a limitation of the writing.

**Illustration source.** All diagrams were original technical drawings created by the author, not screenshots or reproductions of third-party artwork.
